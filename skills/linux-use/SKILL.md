# linux-use

Complete the requested task and leave no unrequested resources or changes behind. Cleanup is part of completion, including after errors. Preserve the user's requested output and anything the user explicitly asks to keep open.

## Own only what you create

- Before opening anything, identify the relevant existing state: `browser_status` for this browser session, or `list_windows` for native windows. Record resources you create and how to close them in the task context, using exact returned identities or session handles. A matching title, URL, or process name does not prove ownership.
- Open the minimum resources needed and close each as soon as its purpose is complete. Choose a supported, targeted cleanup method before creating a resource. Keep a browser open/use/close cycle on the same MCP connection; a new server session cannot release an old session's tab.
- Existing tabs, windows, applications, processes, and user files are borrowed. Do not close them as cleanup. A resource the user takes over becomes user-owned, even if you created it.
- Treat cleanup as a `finally` step: run it on success, failure, blocked work, and cancellation while tools remain available, before handing off or sending the final response. Carry unresolved resource identities into a handoff. Do not rely on MCP exit or extension disconnect to clean up.

## Stealth first, then escalate

Do the work without disturbing the user whenever a route for it exists, and do not stop when none does.

1. Start with the routes that never take focus: the owned background Chrome tab through the browser tools, AT-SPI actions (`click_element`, `set_value`, `invoke_menu`, `run_subtask`), and background delivery. On X11, background pointer input still moves the real pointer, and some toolkits (GTK 3) ignore background clicks; read the window again before building on one.
2. `human_activity` means the user is on the target: keyboard or pointer input in the last two seconds while the target was active or under the pointer. Input this server sent does not count. First look for a route around them, such as a short wait and one retry.
3. If no quiet route can do the work, escalate instead of stopping. Retry the refused call with `allow_while_user_active: true`, and use `delivery_mode: "foreground"`, `bring_to_front` or `restore_window` when the app ignores background input. Do the minimum, then tell the user what you interrupted. `replay_trajectory` never repeats an escalation; escalate the live call instead.
4. Never escalate when the user said they do not want to be interrupted, in this conversation or in their standing instructions. Stop and report what is still pending.

Escalation is about focus and timing only. A consequential action still needs the user's authorization. On the owned Chrome tab, a tab the user selected or moved out of the group is theirs; the browser tools act on it only when retried with `allow_while_user_active: true`, under the same rules.

## Decision-model-first decisions and verification

With `OPENROUTER_API_KEY`, `jev_decide`, `verify_state` criteria and `run_subtask` are answered by `liquid/d1.2-ultra`; Jev (`typesafe/jev-1.14`) answers only when d1.2-ultra is unreachable. `engine` names the model that answered and `fallback_reason` marks a fallback; treat a fallback answer as less calibrated. A Jev key without OpenRouter calls Jev directly.

1. Start with structured evidence: `get_ui_tree` for an AT-SPI window, or `browser_snapshot` for the owned tab. Filtered labels, roles and goal text go to the model, never field values or secrets as text. Native `jev_decide` (with `target_pid` and `target_window_id`) and `verify_state` also send a screenshot of the exact window (1024 px), which shows field contents, unless AT-SPI shows a password field; check `image_attached` and `image_skip_reason`. Do not call them on a window whose pixels the user would not want sent to OpenRouter.
2. Prefer `jev_decide` for the next authorized step; use `browser: true` (or no target) for the owned Chrome tab, which sends labels only. A native proposal names `element_id` and `expected_state_token` for `click_element`. Use `run_subtask` for bounded native multi-step goals (labels, values and window texts only, no screenshot, no keyboard shortcuts). The model is faster and cheaper than screenshot reasoning by the session LLM, not a substitute for user authorization. Without a key, `jev_decide` returns `DEFER_TO_LLM` candidates; do not invent a model result or silently ignore a configured model error.
3. Verify results with `verify_state`: natural-language `expect.criteria`, or `element_exists`, `element_value` and `focused_element` through AT-SPI. Treat `fail` or `unknown` as unverified, not completion. Read screenshots yourself only when the model's answer is unavailable or insufficient.
4. On `BLOCKED`, read `reason`: ask the user when a material action lacks authorization, otherwise observe again or pick a listed alternative only when the goal makes it unambiguous. A high `consequential` signal needs explicit user authorization no matter what the model chose. Pass `allowed_risks` (`delete`, `send`, `purchase`, `close`) only for categories the user's goal explicitly authorizes.

## Sessions, recordings and temporary state

- Before creating a named identity with `start_session`, inspect `get_session_state` and track the returned session and capture scope under the ownership rules above. Do not reuse or end an unfamiliar session. The agent cursor overlay is visual only, click-through and non-focusing; it never moves the real pointer.
- Track every recording you start and its output directory. In the `finally` cleanup, call `stop_recording` for your recording, then `end_session` for each session you started; inspect `get_recording_state` and `get_session_state` to verify cleanup. Do not stop another task's recording. Replay repeats real actions; authorize and verify them as live actions.
- Use `kill_app` only for an exact application PID you launched and still own, never a pre-existing application or one the user took over. Prefer closing the owned window when an application contains borrowed windows.
- If you overwrite the clipboard, first capture enough prior content to restore it safely. Track the overwrite, restore the prior clipboard only if it is still your change, and verify restoration. Never overwrite intervening user activity; if safe restoration is unavailable, do not overwrite it for convenience.
- Keep input in background mode by default. `delivery_mode: "foreground"` temporarily activates the target and restores the prior app; `bring_to_front` is a separate persistent activation. Use either only as described in "Stealth first, then escalate". Window-scope `move_cursor` changes only the overlay; desktop scope moves the real pointer and needs explicit intent.

## Chrome: open, use, close, verify

Use the browser tools for HTTP(S) work through the connected Chrome extension. They operate on one owned background tab per MCP server session; they do not accept arbitrary tab IDs. Tabs opened by linux-use are placed in a collapsed "linux-use" tab group; moving a tab out of the group or selecting it gives control back to the user. The owned tab keeps rendering while it stays in the background, so dialogs, menus and animated pages work there as they do in a visible tab.

All browser actions, including `browser_navigate`, `browser_click`, `browser_type`, `browser_pointer`, `browser_dialog`, `browser_set_input_files`, `browser_download` and `page`, act only on that owned tab. Never use native automation or JavaScript to bypass tab ownership or user takeover. Do not click through a Chrome window with the native tools when a background tab can do the work: web content answers snapshot refs reliably and pixel clicks poorly. Use fresh snapshot refs after mutations. The extension needs `"debugger"`, `"downloads"` and `"tabGroups"` permissions; Chrome shows its yellow debugging bar from `browser_open` until `browser_close`. A JavaScript dialog comes back as `dialog` from the call that opened it, and the other calls return it until you answer it with `browser_dialog`.

1. Call `browser_status` with `{}`. It always answers with a `state`: `connected` means use the browser tools; `busy` means another call is running, so retry shortly; `outdated`, `not_connected` and `not_installed` come with a `hint` to act on or pass to the user. If `hasTab: true`, reconcile it with this task's tracked resources before using or releasing it; do not close an unfamiliar session's work.
2. Call `browser_open` with `{"url":"https://example.com"}`. Record the cleanup obligation as soon as you attempt creation: an error or timeout can occur after a tab was created. Do not open another until this session's previous tab is released.
3. Use `browser_snapshot` with `{}` (or `{"query": "save|cancel"}` to get only matching controls, without the page text) and `browser_act` with the current snapshot's `ref`. `browser_act` waits for the page to settle and returns a fresh snapshot (`settle_ms`, `settled`); refs from the earlier snapshot are stale, so use the new refs. Use fresh observations after other mutations or stale-reference errors. `jev_decide` withholds risky controls (delete/send/purchase/close); pass `allowed_risks` only for categories the user's goal authorizes. Avoid links/actions that spawn extra tabs or windows unless required; the browser tools cannot enumerate or close arbitrary popups.
4. As soon as you have the needed result, call `browser_close` with `{}` on the same connection, including when snapshot, navigation, or an action fails. If an open attempt failed ambiguously, inspect `browser_status` and reconcile ownership before cleanup or another open.
5. Inspect the close result and call `browser_status` again. `closed: true` confirms removal; `released: true` and `hasTab: false` confirm only that the session released its handle. They do **not** prove that the tab disappeared. `closed: false` may mean user takeover, an already removed tab, or failed removal. Never report all tabs closed from release alone.

On `human_activity`, the user selected your tab. Release it through `browser_close`, which leaves the tab they selected open, then `browser_open` a new background tab and continue there if the task still requires it. If the work cannot be redone in a new tab, retry the calls for that tab with `allow_while_user_active: true`, unless the user said not to interrupt them, and tell them what you interrupted. Escalation is about focus and timing only; a consequential action still needs the user's authorization. Do not switch the user's tab away, force-close it through native automation, or reconnect just to regain ownership.

`tab_unresponsive` means the page did not answer within 30 seconds. Its tab was already released, and closed unless the user had selected it. Call `browser_open` again; other sessions were not affected.

The extension makes a best-effort activity check before removal; selection and removal are not atomic. If cleanup is uncertain, do not manufacture proof or accumulate replacement sessions. Use a safe, supported inspection/recovery path for the exact owned resource, or report what remains unverified. Never quit Chrome, close all tabs, or disconnect the shared extension as cleanup.

## Native Linux windows

- Call `doctor` before native work. Native controls require Linux with X11 and the reported utilities; Wayland is unsupported; the AT-SPI element tools need python `gi`/AT-SPI and an application that exposes AT-SPI. Browser extension availability is independent of X11. Do not install utilities or change the desktop session just to bypass an unsupported operation without task authorization.
- Use `list_windows` to select the exact `target_pid` and `target_window_id`. Prefer `get_ui_tree` (pass `query` to read only what you need) and act with `click_element` or `set_value` using its `ax_<n>` ids and `state_token` as `expected_state_token`; `effect: ui_changed` means the window reacted, `unverified` means read again before repeating anything, above all a toggle. `get_accessibility_tree` is only a desktop window summary. For visual fallback, call `screenshot`, inspect its image and metadata, and pass its token as `expected_state_token` to legacy mutations; reobserve after mutations or stale-state errors.
- For visual actions, submit `native_visual_propose` with the exact target/token, one supported action (`left_click`, `type`, `key`, or `scroll`), its parameters, and a `decision` explanation. Execute the returned `proposal_id` with `native_visual_execute` only when the action is authorized. Proposals are single-use and expire; a token is not authorization.
- The `screenshot` tool's image is for the MCP caller's visual model; `jev_decide` and `verify_state` take their own capture for the decision model. `zoom` returns a full-resolution crop whose pixels click tools accept with its token; `cursor_position` remains unsupported, so use `get_cursor_position`. `get_ui_tree`, `click_element`, `run_subtask`, `invoke_menu` and `set_value` require an already installed Python `gi`/AT-SPI runtime; do not install dependencies without authorization.
- `restore_window` explicitly changes focus; use it only when requested and use its returned token afterward. Native input can move the physical pointer, even with background delivery. Check `health_report`: human-activity detection needs `xprintidle` and is reported as skipped when absent. Do not claim protection without it. Use an isolated desktop for unattended input; do not assume X11 targeting makes a shared desktop hermetic. If you cannot avoid interference or safely restore temporary state, stop before sending input.
- There is no native `close_window` MCP tool. Close a task-created window only through an observed close control or a supported exact-window action with a fresh token. Do not kill an application containing user windows, discard user edits, or use blind global shortcuts.

## Other resources and final cleanup

- Close task-created dialogs, windows, and tabs. Stop only task-owned processes, servers, recordings, or automation sessions, using their exact identities. Do not stop shared MCP/native hosts or pre-existing applications.
- Remove only disposable downloads, screenshots, profiles, and temporary files created for this task. Keep requested deliverables. Do not clear shared history, cookies, caches, or other user data to simulate isolation.
- Avoid changing clipboard, focus, window geometry, settings, or permissions for convenience. If an authorized temporary change is necessary, record its prior value and restore it only while it remains your change; never overwrite intervening user activity. If safe restoration is unavailable, choose an isolated environment or stop before changing it.
- Verify cleanup with close results and fresh observations appropriate to the resource, such as `browser_status`, `list_windows`, or exact process/file checks. Check both that owned temporary resources are gone and that borrowed resources remain. Report unresolved cleanup and intentional handoffs briefly.

This skill is an agent workflow, not an automatic sandbox. The current Chrome profile retains normal browsing side effects such as history, cookies, and site state. If the task requires zero persistent browser/desktop state, use an authorized isolated environment; this MCP's shared-profile mode cannot provide that guarantee. Do not undo the actual user-requested changes in the name of cleanup.
